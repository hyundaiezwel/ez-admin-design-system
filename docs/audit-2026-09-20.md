# 설계 원칙 대비 감사 — 10화면

감사일 2026-09-20 / 기준 [설계 원칙](https://hyundaiezwel.github.io/ez-design-system/principles) (`@ezwel/ui` v1.4.0)
방법: 정적 스캔(`scripts/audit-static.mjs`) + 렌더 실측(브라우저 DOM 측정)

눈으로 보지 않았다. 여백은 `getComputedStyle`과 인접 요소 경계 거리로 쟀고,
빈 상태는 실제로 0건이 되는 조건을 넣어 확인했다.

---

## 결론

**"여백이 만족스럽지 않다"의 원인은 감이 아니라 수치로 설명된다 — 전 화면의 여백이
원칙 사다리보다 정확히 한 단계씩 낮다.**

| 역할 | 지금 화면 | 원칙 사다리(compact) | 차이 |
|---|---|---|---|
| 라벨–입력 (intra) | **4px** | 8px | −1단계 |
| 필드끼리 (inter) | **12px** | 16px | −1단계 |
| 조회영역–목록 (region) | **16px** | 24px | −1단계 |
| 카드끼리 (region) | **16px** | 24px | −1단계 |

부등식(그룹 사이 ≥ 그룹 안 × 2) 자체는 통과한다(12 ≥ 8). 비율은 맞는데 **절대값이 낮아서**
전체가 눌려 보인다. 원칙 §2의 "헷갈리면 더 큰 쪽"을 지키지 않은 결과다.

---

## 통과한 것

공정하게 먼저 적는다.

| 항목 | 결과 |
|---|---|
| §2 그룹 사이 ≥ 그룹 안 × 2 | **통과** — 12 ≥ 4×2 (비율 3.0) |
| §2 패딩 ≥ 내부 최대 간격 | **전 화면 통과** (24/20 · 16/12) |
| §4 primary 영역당 하나 | **통과** — 카탈로그만 3개이나 버튼 진열이 목적인 화면이라 의도 |
| §8⑦ 빈 상태 | **목록 4화면 통과** — 0건 조건에서 "조회 결과가 없습니다." 확인 |
| 대비 (별건 측정) | 라이트·다크 0 실패 |
| §3 `position:absolute` | **0곳** |

정적 스캔이 "문의·프로모션 primary 2개", "빈 상태 미정의"로 잡았던 것은 **오탐**이었다 —
전자는 페이지머리와 조회영역이라는 서로 다른 영역이고, 후자는 `TabGrid`의 placeholder가
처리한다. 키워드 기반 판정의 한계라 실측으로 걷어냈다.

## 지적 사항

### 심각 (구조)

**H1 — 앱이 역할 토큰을 아직 못 쓴다**
`--ez-gap-adjacent/intra/inter/block/region`을 조회하면 전부 미정의다(폴백값이 나온다).
앱이 `@ezwel/ui` **v1.3.0**에 물려 있고 역할 토큰은 v1.4.0에 들어갔다.
→ 의존성을 v1.4.0으로 올리는 것이 다른 모든 수정의 선행 조건이다.

**H2 — 같은 역할에 토큰이 두 벌이고 값이 다르다**

| 역할 | v1.3.0 밀도 토큰 | v1.4.0 역할 토큰 |
|---|---|---|
| 영역 사이 (compact) | `--ez-section-gap` **16** | `--ez-gap-region` **24** |
| 영역 사이 (comfortable) | `--ez-card-gap` **24** | `--ez-gap-region` **32** |

화면은 밀도 토큰을 쓰고 있어서 원칙 문서와 실제가 어긋난다. **둘 중 하나가 정본이어야 한다.**
밀도 토큰이 역할 토큰을 참조하도록 묶는 쪽을 제안한다 — 역할이 상위 개념이다.

**H3 — 여백이 한 단계씩 낮다** (위 결론 표)
H1·H2를 풀면 자동으로 따라오는 부분이 크지만, `.field`(4→8)와 `.sfb__fields`(12→16)는
화면 CSS에 직접 박혀 있어 별도로 고쳐야 한다.

**H4 — 오류·로딩 상태가 없다**
10화면 전부 **정상 + 빈 상태만** 그렸다. 원칙 §8⑦은 넷을 요구한다.

| 화면 | 빈 | 오류 | 로딩 |
|---|---|---|---|
| 목록 4종(문의·회원·주문·프로모션) | O | **X** | **X** |
| 대시보드 · 통계 | **X** | **X** | **X** |
| 상품 등록 | — | O(필드 검증) | O(저장 중) |
| 로그인 | — | O | O |

목업이라 비동기가 없는 것이 이유지만, **"정상만 그린 화면은 절반"**이라는 원칙 기준으로는
미완이다. 최소한 `ErrorBanner` 자리와 스켈레톤 자리를 잡아 둬야 실제 API를 붙일 때
레이아웃이 흔들리지 않는다.

### 보통

**M1 — 본문 폭 초과 (§3)**
읽는 문단이 최대 폭(`--ez-measure` 68ch ≈ 780px)을 넘는다.

| 화면 | 폭 | 내용 |
|---|---|---|
| 문의 답변 관리 | **1251px** | 그리드 아래 복붙 안내 |
| 컴포넌트 카탈로그 | **1196px** | 색 스케일 설명 |

→ `.ez-prose` 또는 `max-inline-size: var(--ez-measure)`.

**M2 — px 리터럴 11개 (§9⑦)**
`CatalogPage`(78·30) `DashboardPage`(110·90·96) `InquiryPage`(10·44) `LoginPage`(360·40)
`MemberPage`(96).
표 열 너비처럼 토큰화가 부적절한 것도 섞여 있다 — **판단해서 남길 것은 주석으로 이유를 남긴다.**

**M3 — gap 리터럴 2px**
`CatalogPage` · `StatsPage`. 스와치 사이 간격인데 스케일에 2px이 없다.
→ `--ez-space-05`(2px)를 만들거나 4px로 올린다.

### 낮음

**L1 — 개별 margin (§3)** 대시보드 5 · 문의 5 · 프로모션 6곳.
Stack/Cluster의 `gap`으로 대체 가능한지 검토 대상. 전부 나쁜 것은 아니다(광학 보정 포함).

**L2 — `tabular-nums` 누락** `PromotionPage` 예산·집행률 열.

**L3 — hex 리터럴** `LoginPage`의 `#fff` 1개 → `--ez-text-inverse`.

## 고치는 순서

앞의 것이 뒤의 것을 줄인다.

1. **의존성 v1.4.0** (H1) — 선행 조건
2. **밀도 토큰을 역할 토큰에 묶는다** (H2) — 정본을 하나로. H3의 절반이 여기서 풀린다
3. **`.field` 4→8, `.sfb__fields` 12→16** (H3) — 화면 CSS 직접 수정
4. **오류·로딩 자리 잡기** (H4) — 목록 4종 + 대시보드·통계
5. M1~M3, L1~L3

1~3까지만 해도 "눌려 보이는" 인상은 사라진다.

## 감사 자동화

`scripts/audit-static.mjs`는 커밋마다 돌릴 수 있다. 다만 **키워드 판정이라 오탐이 난다** —
이번에도 6건 중 4건이 오탐이었다. CI에 물리려면 실패로 끊지 말고 **보고서로만** 남기고,
여백 비율처럼 렌더해야 아는 것은 별도 실측이 필요하다.

## 조치 결과 (2026-09-20 같은 날)

지적 5군 전부 반영했다. **정적 23건 → 3건**, 남은 셋은 low(개별 margin)뿐이다.

### 여백 사다리 — 재실측

`getComputedStyle` 선언값과 인접 요소 경계 거리를 둘 다 쟀다. 둘이 일치한다.

| 역할 | 감사 시점 | 지금 | 원칙(compact) |
|---|---|---|---|
| 라벨–입력 (intra) | 4px | **8px** | 8px |
| 필드끼리 (inter) | 12px | **16px** | 16px |
| 조회영역–목록 (region) | 16px | **24px** | 24px |
| 카드 패딩 (block) | 16px | **20px** | 20px |

9화면 전수 통과(로그인 제외). 부등식 16 ≥ 8×2 통과. 본문 폭 초과 **0곳**.

밀도 전환도 한 축으로 묶였다 — comfortable에서 intra 8 / inter 20 / block 24 /
region 32로 **역할 토큰만 올리면 카드 패딩·섹션 간격이 따라온다**(H2 해소).

### 상태 넷 — 실행 확인

`useMockQuery` + `QueryState`를 넣고 문의 화면에서 네 상태를 실제로 돌렸다.

| 상태 | 조건 | 결과 |
|---|---|---|
| 로딩 | 조회 직후 120ms | 스켈레톤 10개 |
| 정상 | 기본 | 20행 |
| 빈 | 없는 검색어 | 빈 상태 문구 O |
| 오류 | 검색어에 `오류` | `role="alert"` + 다시 시도 |

오류일 때 스켈레톤 **0개** — 실패한 조회에 로딩을 겹쳐 보이지 않는다.

### 감사기도 고쳤다

지난 회차에 6건 중 4건이 오탐이었다. 판정을 영역·화면 유형 인지로 바꿨다.

- primary 개수는 모달·드로어를 별도 영역으로 빼고 센다 — 페이지머리와 조회영역을
  한 덩어리로 보던 것이 오탐의 원인이었다
- 빈 상태는 **목록이 있는 화면에만** 요구한다. 로그인에 "결과 없음"을 요구하면
  틀린 건 화면이 아니라 규칙이다

## 이 감사가 찾지 못했을 뻔한 것

수정 중에 **원래 지적에 없던 실제 장애**가 나왔다. 기록해 둔다.

**`.ez-grid` 이름 충돌 — 표 본문 높이 0px**

H1(의존성 v1.5.0 올리기)을 실행한 순간 네 개 그리드 화면의 표 본문이 사라졌다.

| | |
|---|---|
| 원인 | 어드민이 Tabulator 래퍼로 쓰던 `.ez-grid`를 디자인 시스템 v1.4.0이 `display: grid` 레이아웃 프리미티브로 선언 |
| 증상 | `.tabulator-header` 458px / `.tabulator-tableholder` **0px** (표 460px를 헤더가 전부 먹음) |
| 신호 | **없음.** 콘솔 오류 0, 타입 검사 통과, 정적 감사 통과 |
| 조치 | 어드민 쪽을 `.ez-datagrid`로 개명. 복구 후 헤더 57px / 본문 401px |

**정적 감사도 타입 검사도 이걸 잡지 못한다.** 그래서 감사기에 예약 클래스 검사를
추가했다 — 예약어를 문서에 박지 않고 설치된 `dist/layout.css`에서 읽어 대조한다.
`.ez-grid`를 다시 정의한 파일을 넣어 검사기가 실제로 잡는지 확인했다(1건 검출).

디자인 시스템 쪽에도 [도입 §1-6](https://hyundaiezwel.github.io/ez-design-system/adoption)을
추가했다(v1.5.1). **공개 클래스 이름은 API다** — 늘릴 때 소비자에게 알려야 한다.
