# 셸 규칙 — 사이드바와 탭

셸(헤더·사이드바·탭 바)은 `@ezwel/ui`가 **일부러 안 만든 조각**이다. 프로젝트마다
정보구조가 다르기 때문이다. 그래서 규칙은 여기 있고, 굳으면 디자인 시스템 승격 후보가 된다.

수치는 전부 [설계 원칙](https://hyundaiezwel.github.io/ez-design-system/principles) §2의
역할 토큰과 크기 스케일에서 고른다. 아래 표의 px는 **스케일 위의 값**이지 새로 만든 값이 아니다.

---

## 1. 참조한 것

[Sidebar with Interactive Prototype](https://www.figma.com/design/LKYmck9HPNQ6TudMu16TqI/Sidebar-with-Interactive-Prototype--Community-)
(Figma Community). 저자가 파일 안에 원칙 여덟을 적어 뒀다.

| # | 원문 | 우리 해석 |
|---|---|---|
| 1 | Logo in the header enhancing branding | 브랜드는 **한 곳에서만** 말한다 |
| 2 | General and professional logo solution | 마크 + 워드마크, 접히면 마크만 |
| 3 | To support the architecture I would like a search field | 검색은 메뉴 위에, 행과 같은 폭 |
| 4 | Quickly find my main pages | 주 메뉴는 스크롤 없이 한눈에 |
| 5 | Highlights the states of menu items to be more intuitive | 상태는 **보여준다**, 암시하지 않는다 |
| 6 | Informs the number of notifications or tasks available | 건수는 그 행 위에 |
| 7 | Being able to quickly access my profile settings | 나에 관한 것은 아래에 고정 |
| 8 | Supports expanding and collapsing the sidebar | 접기는 기능이지 장식이 아니다 |

### 가져오지 않은 것과 그 이유

참조 파일에는 **헤더가 없다.** 그래서 브랜드(1·2)·검색(3)·프로필(7)이 전부 사이드바에 있다.
우리 셸은 헤더가 따로 있고 거기서 셋을 이미 말한다.

**그대로 옮기면 중복이 된다.** 같은 것을 두 곳에서 말하는 화면은 사용자가 어느 쪽이
정본인지 매번 판단해야 한다. 규칙은 가져오고 재고(inventory)는 가져오지 않는다.

| 참조 원칙 | 우리 셸에서 답하는 곳 |
|---|---|
| 1 · 2 브랜드 | 헤더 좌측 (`AppHeader`) |
| 3 검색 | 헤더 중앙 통합 검색 |
| 7 프로필 | 헤더 우측 아바타 |
| 8 접기 | 헤더 좌측 햄버거 — **사이드바로 옮기지 않았다** |

8번만 판단이 갈렸다. 참조는 접기 버튼을 사이드바 머리에 둔다(제어 대상 옆에 두는 것이
맞다는 논리다). 우리는 헤더에 둔 채로 남긴다 — **컨트롤이 둘이 되는 것이 위치가
덜 이상적인 것보다 나쁘다.** 하나를 옮기면 다른 하나를 지워야 하는데, 헤더 좌측
햄버거는 업무 시스템에서 굳은 관습이라 지우는 쪽의 비용이 더 크다.

## 2. 사이드바 규칙

### 2-1. 두 구역으로 나눈다

참조는 셋(브랜드·검색 / 주 메뉴 / 유틸리티·프로필)이고, 우리는 위 구역을 헤더가
가져갔으므로 **둘**이다.

```
┌──────────────┐
│ 주 메뉴       │  flex: 1, 넘치면 여기만 스크롤
│ …            │
│              │  ← 남는 공간은 전부 여기로
├──────────────┤
│ 도움말·환경설정 │  하단 고정
└──────────────┘
```

**남는 공간이 어디로 가는지가 규칙이다.** 주 메뉴가 늘어나도 하단 구역은 바닥에
붙어 있어야 한다 — "가는 곳"과 "시스템에 관한 것"은 성격이 다르고, 성격이 다르면
자리가 고정이어야 찾는 비용이 0이 된다.

메뉴가 길어졌을 때 스크롤은 **주 메뉴 구역에만** 건다. 사이드바 전체가 스크롤되면
하단 구역이 화면 밖으로 밀린다.

### 2-2. 폭은 둘 다 고정이고, 비율을 지킨다

참조에서 편 폭과 접은 폭의 비가 **약 3.75:1**이었다(화면에서 잰 값이다. 커뮤니티
파일이라 정확한 px는 못 읽는다). 그 비를 우리 스케일 위의 값으로 옮긴다.

| | 값 | 근거 |
|---|---|---|
| 편 폭 `--lnb-w` | **240px** | 2depth 라벨 최장 "프로모션 등록·관리"가 들어간다 |
| 접은 폭 `--lnb-w-collapsed` | **64px** | 240 ÷ 3.75. 아이콘 20 + 좌우 22 |

**접힘은 좁은 사이드바가 아니라 레일이다.** 라벨을 잘라서 보여주지 않는다 —
잘린 글자는 정보가 아니라 소음이다. 레일에서는 아이콘만 남기고, 하위 메뉴는
플라이아웃으로 낸다(참조는 접히면 하위에 도달할 길이 없다. 이건 우리가 낫다).

### 2-3. 행 리듬 — 라벨이 한 축에 선다

| | 값 |
|---|---|
| 행 높이 | `--ez-size-lg` **40px** |
| 행 사이 | `--ez-space-0-5` 2px (붙은 것) |
| 아이콘 상자 | **20px 고정** |
| 아이콘–라벨 | `--ez-gap-intra` 8px |

아이콘 상자를 고정하는 이유는 하나다 — **아이콘 폭이 제각각이면 라벨 시작점이
행마다 흔들린다.** 눈이 세로 한 줄을 따라가지 못하면 목록을 읽는 속도가 떨어진다.

2depth 행은 **1depth 라벨과 같은 축**에서 시작한다. 들여쓰기를 더 하지 않는다 —
계층은 이미 글자 크기와 색으로 말했고, 거리로 또 말하면 두 번 말하는 것이다
(원칙 §1 공리 ④).

### 2-4. 상태는 보여준다 (참조 5)

활성 행은 **배경 + 색 + 좌측 표시자** 셋으로 말한다. 색 하나로는 안 된다 —
고대비 모드와 색각 이상에서 무너진다.

| 상태 | 표시 |
|---|---|
| 활성 | 배경 `--ez-surface-selected` + 글자 `--ez-text-brand` + 좌측 3px 막대 |
| 그룹이 활성 화면을 품음 | 배경 없이 글자만 강조 — 활성 행과 구별돼야 한다 |
| hover | 배경 `--ez-surface-hover` |

### 2-5. 건수는 그 행 위에 (참조 6)

처리할 것이 쌓이는 화면은 행 오른쪽에 건수를 단다. **숫자를 쓴다** — 점만 찍으면
"뭔가 있다"까지만 전달되고 "지금 봐야 하나"는 전달되지 않는다.

레일(접힘)에서는 숫자가 안 들어가므로 점으로 낮춘다. 대신 `aria-label`에 건수를
남겨서 스크린리더에서는 정보가 유지되게 한다.

## 3. 탭 규칙

### 3-1. 폭은 고정이다

탭 폭을 내용에 맞추면 **탭을 열 때마다 이미 열려 있던 탭이 움직인다.** 같은 탭이
같은 자리에 있어야 손이 기억한다(Fitts + 위치 기억).

| | 값 |
|---|---|
| 탭 폭 `--tab-w` | **180px 고정** |
| 넘치는 라벨 | 말줄임. 전체 라벨은 `title`로 남긴다 |

180px은 여유값이다 — 2depth 최장 라벨("프로모션 등록·관리", 12자)이 12px에서
약 144px이고 닫기 버튼 18 + 좌우 여백 18을 더하면 180에 들어간다.

라벨이 짧아도 폭은 줄이지 않는다. **고정이라는 것이 규칙의 전부다.**

### 3-2. 닫으면 왼쪽으로 간다

방금 닫은 자리의 오른쪽 탭으로 가면 커서가 이미 그 위에 있어 연속으로 닫다가
엉뚱한 화면을 연다. 왼쪽으로 간다.
